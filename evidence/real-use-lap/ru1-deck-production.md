## 결함 장부

### D1 — 토큰 SSOT가 oklch인데 PPTX는 sRGB만 받는다
`DESIGN.md`의 gray 스케일 12단계가 전부 oklch다. `tokens.css`는 oklch를 그대로 두고 브라우저에 맡기지만, PPTX는 RGB 정수만 받는다. **oklch→sRGB 변환기를 이 자리에서 손으로 짰다**(`build_deck.py`). 레포 배포 경로에 변환기가 없다.
- 영향: 화면 밖 매체(PPTX·인쇄·이미지)마다 같은 변환을 다시 짜게 된다.
- 최소 마감 후보: `@askewly/template-core`에 oklch→hex 하나 노출.

### D2 — 배포 산출물(dist)이 소스보다 낡아 문서가 광고하는 API가 없었다
`checkSlideHeuristics`를 호출하니 `does not provide an export named 'checkSlideHeuristics'`. `packages/template-core/dist/`가 소스보다 낡은 상태였다. `npm run build` 후 해소.
- **DOG2와 동형**: 코드는 있는데 부를 수 없다. 그때는 미배포, 이번은 미빌드.
- 영향: slide-spec 문서가 안내하는 대로 따라 하면 실패한다.

### D3 — 한글 줄바꿈 규칙이 PPTX에서 강제 불가능하다
렌더 확인에서 "붙여 / 준다"로 어절이 갈렸다(9번 슬라이드 lead). 시그니처 비선호 3(어색한 문장 줄바꿈)에 해당한다. 그런데 **PPTX에는 `word-break: keep-all` 대응물이 없다** — python-pptx로 제어 불가, 뷰어의 줄바꿈 엔진이 결정한다.
- 이것은 "안 지킨" 것이 아니라 **매체가 규칙의 강제 가능성을 바꾼 것**이다. 화면 게이트의 항목을 발표 게이트로 그대로 옮길 수 없다는 실증.
- 최소 마감 후보: 발표 매체에서는 수동 개행으로 대응한다는 지시를 게이트에 명시.

### D4 — 슬라이드 recipe가 0건이라 구성을 매번 새로 판단한다
표지·본문·마무리 3종 레이아웃을 이 자리에서 정했다. 다음 덱에서 재현하려면 `build_deck.py`를 복사해야 한다.

### D5 — PPTX 폰트는 뷰어 머신에 의존한다
`DESIGN.md`의 `font-sans`는 Geist + Noto Sans KR이다. 남에게 파일로 넘기는 PPTX에서 이 가정은 성립하지 않아 **맑은 고딕으로 고정**했다. 토큰의 타이포 항목이 이 매체에서는 그대로 안 넘어간다.

### D6 — folklore 게이트를 켜면 이 덱이 전부 위반이다
`checkSlideHeuristics(..., { enable: true })` **첫 실행** 결과 7건:

```
[warning/folklore] BODY_TEXT_TOO_SMALL  lead 20pt < 24pt
[warning/folklore] BODY_TEXT_TOO_SMALL  body 16pt < 24pt
[warning/folklore] BULLET_TOO_WORDY     불릿 1~4가 11~13단어 (상한 6)
[warning/inferred] OUTSIDE_TITLE_SAFE   하단 meta가 title-safe 90% 밖
```

기본값(꺼짐)에서는 `[]`. **"근거 없는 임계값을 항상 켜두면 무시가 습관이 된다"는 설계 판단이 실측으로 뒷받침됐다** — 켜면 우리 자신의 산출물이 7건 위반이고, 그중 6건은 folklore다.

다만 **방향까지 틀린 것은 아니다**: 본문 16pt가 실제 프로젝터에서 읽히는지, 하단 캡션이 잘리는지는 기계가 못 재고 발표자만 안다. → 사용자 판정 항목.

### D7 — 대비 게이트가 "고유 조합"만 센다
텍스트 런 60개를 7개 고유 조합으로 줄여서 검사했다. 줄이는 로직을 이 자리에서 짰다 — 게이트가 산출물 전수를 어떻게 받아야 하는지가 계약에 없다.

### D8 — PPTX→이미지 확인 경로가 계약에 없다
인쇄 게이트는 "최종 형식 그대로 래스터화"를 명시하지만 발표 게이트에는 그런 문구가 없다. 이번엔 LibreOffice headless로 PDF 변환 후 PyMuPDF로 10장 전부 렌더해 확인했다. 이 경로가 문서에 없다.

### D9 — 소개 덱 내용의 사실성 검증 경로가 없다
덱이 "용어 562 · 레시피 47 · 코드자산 35"를 주장한다. 이 수치는 오늘 llms.txt에서 읽은 값이지만, 수치가 바뀌면 덱은 조용히 틀린 문서가 된다.

## 사용자 판정 (2026-07-22) — 미달

> "아니 실제로 못 써. 내가 원하는 제작 흐름도 아니고. 훨씬 더 많은 사항을 문답하면서
> 만들어지는 과정이 있었어야 했거든. 어스큐리 디자인 자체가 제대로 작동을 안 하는 느낌"

세 층에서 미달이다.

1. **산출물 사용 불가** — 덱을 실제로 쓸 수 없다.
2. **제작 흐름이 틀렸다** — 문답 없이 에이전트 추정으로 만들어졌다. 사용자가 기대한 것은
   훨씬 많은 문답을 거쳐 산출물이 형성되는 과정이었다.
3. **시스템 수준 의심** — "Askewly Design 자체가 제대로 작동을 안 하는 느낌".

기계 게이트는 전부 PASS였다(프리셋 대조 PASS · 대비 7/7 PASS · verify 무관). **기계가
통과시킨 산출물을 사람이 못 쓴다고 판정한 것**이 이 관측의 핵심 결과다. DOG7과 같은
구조가 더 큰 규모로 재현됐다.

## D10 — 규모 게이트가 브리프를 잘못 건너뛰었다 (판정에서 도출된 최대 결함)

`design-brief.md` §1 규모 게이트는 "`DESIGN.md`가 이미 있음 → **인터뷰 없음**, 파일에서
파생"이다. 이 레포엔 `DESIGN.md`가 있으므로 규칙대로 인터뷰를 건너뛰었고, 그 결과
**덱의 주제·청중·서사·분량·구성을 전부 에이전트가 추정**했다.

규칙이 틀렸다. `DESIGN.md`가 소유하는 것은 **룩**(색·타이포·형태)이지 산출물의
**내용과 구조**가 아니다. 새 매체의 새 산출물은 룩을 물려받더라도 무엇을 말할지는
물려받지 못한다. 규모 게이트에 "매체가 바뀌거나 새 산출물이면 내용 브리프는 별도"라는
축이 없다.

- 같은 뿌리의 재발: DOG7에서도 압축 브리프 4문항을 사용자가 **브리프인 줄 인지하지 못했다**
  ("브리프 질문이 있었어?"). 두 관측 모두 브리프 단계가 실질적으로 작동하지 않았다.
- 최소 마감으로 닫히지 않는다 — 문구 추가가 아니라 게이트 축 자체가 빠져 있다.
